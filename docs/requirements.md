# 3.1 赛道需求与验收矩阵

本文件将指南内容转换为项目需求，供实现、复核和提交准备使用。**矩阵中的真实环境验收证据仍为预期证据，不表示这些真实验证已完成。** 用户已明确选择 RTL 单 track，目前没有 AMD Linux/EDA 环境，要求先完成本机可做部分。

当前本机首版已完成，软件测试规模与结果以当前 `unittest discover` 实测及 [审计修复记录](audit_fixes_20261014.md) 为准；`run_pair` 提供单题 baseline/agent 配对，`scripts/batch.py` 提供串行多题多种子配对，配对回放明确标记为 mock。公开题集导入、划分、批处理和 HTTP mock 联调已完成；真实模型、EDA、AMD 部署验收留待后续接入实际资源。

## 基线公平性核验表

以下前六项直接对应指南 3.1.5.2；其余为提高实验可解释性的工程做法。

- [ ] `run_baseline.sh` 与 `run.sh` 指向同一推理服务、同一模型版本。
- [ ] baseline 和 agent 使用同一上下文配置。
- [ ] baseline 提示词仅含题目，不加入技能、示例、修复建议或额外设计模板。
- [ ] baseline 只产生一次生成请求，不进行模型生成重试。
- [ ] baseline 不调用 EDA 或其他工具辅助生成，不读取技能包。
- [ ] 两者结果在同一次运行中产出，具有共同运行 ID。
- [ ] 记录相同或明确配对的采样配置和种子策略；任何差异在报告中披露。
- [ ] baseline 生成后可由统一评测器评判输出；必须把这种事后评测与 baseline 生成过程调用工具区分开。
- [ ] 保存所有题目结果，失败、超时和基础设施异常均保留，避免只展示成功题。
- [ ] 增益表从配对原始记录生成，不混入其他模型、历史配置或不同数据集的成绩。

## pass@1/pass@5 与通过率口径

指南明确要求报告这两个指标，但当前附件没有给出完整计算规则，不能自行宣布五个候选是否独立、内部修复是否计入尝试或采用何种估计公式。实现应保留题目 ID、采样/尝试 ID、修复轮次、配置、候选代码、各级判定和耗时，使最终统计可以依据官方细则重算。

开发期可以另报明确命名的“首次候选通过率”“修复后通过率”“每题候选数”和分级成功数。这些属于开发统计，不能在细则未确认时改称官方 pass@1/pass@5。禁止生成未经测量的性能数字、填充虚构结果，或将 mock 成绩放入实测表。

## 隐藏题、冻结与数据访问边界

1. 官方隐藏题、测试台、参考实现和评分器不能视为智能体可访问的开发材料。默认只给智能体题面及明确允许的反馈，最终按官方协议实现。
2. 开发数据应在调参前固定划分，记录版本和哈希。公开数据可能与模型训练数据有重合，不把公开集成绩直接解释为未见题泛化成绩。
3. 提交前冻结源码、技能、权重、配置、容器及必要资产清单。清单应能定位文件内容与构建来源，避免只记录一个无法复核的版本名称。
4. 评测窗口内不因看见隐藏题而修改源码、技能或模型；提交包哈希与作品提交阶段一致。
5. 如官方明确允许某种运行期状态或缓存，应记录其边界；在未明确前不把隐式学习或累计题解写入冻结技能包。
