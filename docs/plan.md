# 3.1 RTL/HLS 本地智能体设计赛道：详细实施计划

用户已明确选择 **RTL 单 track**。代码生成目标为 Verilog/SystemVerilog，验收工具链为 AMD Vivado 2025.2。项目目标是交付可离线运行、利用工具反馈提高硬件代码正确率的本地智能体，以及可公平比较的同模型裸跑基线。

本文记录实施顺序和验收方法，**不表示真实模型推理、EDA 验证、数据集评测、AMD GPU 部署或参赛提交已经完成**。用户目前没有 AMD Linux/EDA 环境，当前任务范围是先完成本机可做部分。本机首版已完成，软件测试规模与结果以当前 `unittest discover` 实测及 [审计修复记录](audit_fixes_20261014.md) 为准；单题 baseline/agent 配对回放明确标记为 mock。真实模型、EDA 和 AMD 环境待接入，真实比赛结果需要后续资源验证。

### 阶段 1：固化需求和可替换接口

1. 将指南逐项转换为 [需求和验收矩阵](requirements.md)，区分硬性要求、推荐做法与尚待官方明确的事项。
2. 按用户确认的 RTL 方向实施，首版维护一套 RTL 工具链。
3. 定义内部单题格式：题目、题目 ID、输出目录及允许的题目约束。内部格式只是开发约定，之后通过适配器接入官方格式。
4. 定义运行记录：运行 ID、代码版本、数据集版本、模型标识、推理配置、种子、工具版本、耗时、每次候选和各级结果。
5. 记录尚缺资源：官方基础镜像/入口协议/预算、本地权重、可用推理服务、Vivado 2025.2、ROCm 和 AMD 验证平台。

**交付物：**本计划、需求矩阵、配置说明和未定事项清单。**验收：**每项强制要求都有预期证据；任何“暂定”选项均不会被写成官方结论。

### 阶段 2：实现软件骨架与公平基线

1. 实现标准库 Python 推理客户端，明确网络超时、响应解析、空输出、异常状态及重试边界；正式运行仅连接容器内部或明确配置的本地推理服务。
2. 实现 `run.sh` 的读题、提示构建、生成、工具反馈、有限次修复和代码导出流程。
3. 实现 `run_baseline.sh`：提示词只有题目，单次生成，不读取技能、不调用验证工具、不做生成重试；与 agent 复用相同模型服务和上下文配置。
4. 实现单题配对运行流程，由 `run_pair` 在同一运行 ID 下执行该题的 baseline 和 agent，并保存共同配置快照；公开题集已导入与划分、批处理已实现；真实批评测留待阶段 4。除指南明确要求外，采样参数和种子策略也应尽量配对并完整记录，以减少混杂因素。
5. 给 agent 设置有限的修复轮数、单题总时间和单次输出上限；记录预算耗尽和工具缺失，禁止将这些状态记作通过。
6. 使用 mock 服务/工具测试正常流程、编译失败后修复、不可恢复失败、超时、畸形响应、预算耗尽和结果配对。mock 输出标记为演示或软件测试证据，不进入真实成绩表。

**交付物：**客户端、两个入口、控制流、配置和测试。**验收：**控制流可重复；baseline 确认只有一次生成；缺少真实后端或 EDA 时产生明确错误；测试不依赖网络权重下载或假装存在的工具。

### 阶段 3：接入并核验 Vivado 判定链

1. 固定 Vivado 2025.2；记录实际工具版本，并拒绝把不匹配版本的结果直接标为官方等效结果。
2. 实现 `xvlog` 分析、`xelab` 展开、`xsim` 仿真和 `synth_design` 综合适配；严格执行前一级通过后才进入下一级。
3. 综合目标固定为 `xczu3eg-sbva484-1-e`，应用 5 ns 时钟约束；保存约束、Tcl、日志和网表存在性证据。
4. 区分编译错误、仿真断言/逐拍不一致、仿真超时、综合错误与基础设施错误。工具退出码不能单独替代测试台通过判定。
5. 用已知正确、语法错误、功能错误、不可综合的最小例子检查适配器是否正确分类；实际运行后才将此阶段标为通过。
6. 生成代码仅在受限目录和受控子进程内运行；命令参数结构化传递，避免把模型文本当作 shell 命令。

**交付物：**EDA 适配、最小验证样例及真实工具日志。**验收：**RTL 末级通过必须同时具有前两级通过、综合无 ERROR 和产出网表的证据。指南没有把时序收敛列为末级通过条件，不自行增加这项官方门槛。

### 阶段 4：选择模型并建立公开集实测基线

1. 获取和校验公开数据集；保存仓库提交、题目列表、测试方法和许可信息。
2. 在调参前划分开发集与保留集。开发集可用于提示词和技能迭代；保留集用于检查泛化，避免依据保留集逐题定制技能。
3. 候选模型先按开源权重、许可、可本地部署、AMD 后端兼容及单卡显存可行性筛选，再进行真实小样本比较。候选名称、版本、量化和取舍原因均由实际调查/测试填入，本文不预设最优模型。
4. 实测完整服务的显存峰值，包括权重、KV cache 和后端工作区；仅按参数量或权重文件大小估算不能证明 32 GB 合规。
5. 在同一次配对运行中生成 baseline 和 agent 结果；保留逐题、逐候选的原始记录，报告分级通过率、失败原因和墙钟时间。
6. 为 pass@1/pass@5 保存所需原始样本数据。官方定义未明确前，开发统计清晰命名并标记口径，不能声称是官方指标；agent 内部修复轮数不等于 pass@5 的五个独立尝试。

**交付物：**候选模型比较记录、首轮真实结果、`model/MODEL.md` 的已验证字段。**验收：**每个性能或显存数字可回溯至原始日志；baseline 和 agent 使用同一模型服务及上下文；未测字段明确写“待验证”。

### 阶段 5：以失败为依据优化智能体和技能包

1. 根据真实失败统计排序：接口不匹配、位宽与 signed、复位、阻塞/非阻塞赋值、锁存器、逐拍时序、综合限制等，仅保留实际观察到或有明确依据的诊断规则。
2. 针对编译、仿真、综合反馈分别设计修复提示；保留题目和必要接口，裁剪重复日志，避免无界上下文增长。
3. 设置修复停止条件：成功、无有效进展、相同错误反复出现、总预算耗尽。成功结果必须经完整判定链确认，不能因代码看起来正确而结束为通过。
4. 将已验证的经验写成可复用技能：适用条件、问题模式、建议修复、来源、验证方法、已知局限。
5. 做必要消融：裸跑、仅模板、增加反馈、增加技能、完整方案。比较相同数据和服务下的增益及成本，防止把改变模型或预算带来的差异算作技能增益。
6. 优先提高一次成功稳定性，再探索额外搜索；优化日志裁剪、输出上限和无效重试。只有现有失败证据表明需要且资源可承受时，再考虑微调或 HLS 扩展。

**交付物：**技能包、消融记录、失败分类、经验证的配置。**验收：**能指出哪些设计提高了哪些题型的通过率，以及新增墙钟代价；不能只给出挑选成功样例的视频或单次最好结果。

### 阶段 6：AMD 单卡与断网容器验收

1. 基于官方基础镜像编写并构建最终 Dockerfile；基础镜像未取得时，只能提供开发构建说明或显式待填配置。
2. 验证推理后端、模型量化格式与 AMD GPU 的实际兼容性。指南列出验证平台 W7900 48 GB 和决赛 R9700 32 GB；在 48 GB 卡上跑通不自动证明最终 32 GB 部署成功。
3. 获取全部必要运行资产并固定版本与校验和；关闭运行期模型下载和外网依赖。
4. 在干净环境中启动推理服务，执行配对入口和 EDA 链；断网执行公开样例及覆盖错误路径的样例。
5. 实测峰值显存、单题耗时和整体墙钟。并行度必须在官方预算内，不通过跨卡分片规避约束。
6. 将复现过程交由未参与日常调试的执行者或清洁脚本重跑，记录任何手工步骤并将必要步骤脚本化。

**交付物：**可重建容器、启动配置、资产清单、离线验收日志。**验收：**指定 AMD 环境真实运行成功，完整容纳于单张 32 GB 卡；不依赖开发机缓存、未打包文件或外网服务。

### 阶段 7：报告、冻结和提交准备

1. 阅读最终评分细则，核对入口、预算、pass 统计、模型声明、镜像和提交格式，修正与开发约定不同的适配部分。
2. 完成 `REPORT.md`：架构和依据、模型候选及放弃原因、控制流、重试与回退、上下文管理、技能来源及验证、公开集实测、失败分析、复现说明。
3. 完成 `MODEL.md`：模型来源和版本/权重校验和、量化、实测显存、上下文；如微调，增加基座、方法、训练数据来源和微调权重开源地址。
4. 对源码、技能包、权重、配置、镜像及提交资产生成清单和校验和，并记录构建信息。以只读归档保存最终提交版本。
5. 用冻结包重新执行小规模公开验收，确认入口和资产完整。官方评测窗口中使用同一冻结包，不改源码、技能或权重，不依据隐藏题补规则。
6. 保存盲测输入标识、允许运行的日志和结果；只按官方许可处理题集和反馈。实际提交行为及回执与工程包完成状态分别记录。

**交付物：**完整方案包、最终报告、模型声明、哈希清单和复现命令。**验收：**所有声称的实测结果有证据，官方必交项齐全，冻结哈希与作品提交阶段一致；没有实际提交回执时不能写“已提交”。

## 评分导向与优先级

指南 3.1.5.5（PDF 第 12 页／页脚第 9 页）列出以下权重；精确公式、阈值和预算仍以后续细则为准。

| 评分项 | 权重 | 本计划的优化重点 |
| --- | ---: | --- |
| 能力：题集加权通过率 | 30 | 先满足完整分级判定，重点提高可综合的末级通过率 |
| 增益：同模型裸跑基线提升 | 40 | 同批配对实验、工具反馈修复、有效技能；避免混入模型变化因素 |
| 代价：墙钟效率 | 10 | 减少无效重试和过长输出，记录端到端成本 |
| 智能体与技能包工程质量 | 20 | 可复现流程、诊断、有效性证据、可复用技能和清晰报告 |

执行优先级是：真实工具闭环和公平测量 → 有依据的修复与技能 → 单次稳定性和效率 → 必要时再微调或扩展。不会把扩大模型或增加尝试次数当作自动获得增益分的保证。

## 主要风险与应对

| 风险 | 影响 | 应对和验收边界 |
| --- | --- | --- |
| 官方细则或接口尚未取得 | 开发接口可能与提交接口不同 | 适配层隔离；获取后重新验收，暂不声称最终合规 |
| 当前没有 EDA、模型或 AMD GPU | 无法产出真实通过率与部署结果 | 先完成软件框架；对应真实验证保留待办，mock 不计成绩 |
| 推理后端/量化与 R9700 不兼容 | 在其他 GPU 跑通仍无法决赛部署 | 尽早在目标环境验证，保留更保守可运行配置 |
| 上下文或并发导致显存溢出 | 模型权重能装入但服务运行失败 | 测整个服务的峰值显存，限制上下文/并发并记录配置 |
| baseline 不公平 | 增益不可解释或不满足要求 | 共用服务/上下文，同次运行，保留原始提示和调用记录 |
| 公开集过拟合或隐藏数据泄漏 | 无法证明泛化且破坏评测边界 | 固定开发/保留划分；隐藏参考实现默认不可访问 |
| 重试预算膨胀 | 得分增益被时间成本抵消 | 每题总预算、重复失败停止条件、成本消融 |
| 冻结后修改资产 | 哈希与作品提交不一致 | 只读归档、清单校验；窗口内不改源码、技能和权重 |

## 完成状态如何判定

- **软件首版完成：**代码、入口、配置、文档和 mock 测试达到阶段 2 的出口；只证明软件流程。
- **真实工程验证完成：**阶段 3–6 的 EDA、模型、数据集、单卡和离线验收都有原始证据。
- **参赛方案完成：**阶段 7 的最终细则核对、报告和冻结包完成；实际参赛提交另以官方回执确认。

未满足后两层条件时，交付说明必须明确剩余资源和待验收项。
